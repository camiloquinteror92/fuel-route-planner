Measured, not guessed

python manage.py benchmark plans a coast-to-coast trip inside one process, without network, many times, and saves what it measured in data/benchmark.json; /api/stats serves it with the machine it ran on.

Where the time goes

What each kind of request costs on this server. The slow part of a new trip is not our code: it is the one call to the public routing server.

How it would grow

Each step solves one problem. None is needed today; take a step when its problem shows up, in this order.

  1. Share the caches in Redis

    Solves: each server process keeps its own caches and counters in memory. With several processes the same trip can call the routing server once per process, a what-if is only free on the process that has the route, and the rate limit counts per process.

    Needed when: more than one process or machine serves the API.

    Here: one setting, CACHES to RedisCache, plus pip install redis; the plan cache, the route cache and the rate limit then work across processes. The single flight of the routing call, the pacing of Nominatim, the counters of /api/stats and the test runner's lock stay per process: sharing them needs a lock in the cache (cache.add).

  2. Run our own OSRM

    Solves: the public demo server has no service guarantee, asks for about one request per second and only knows cars. Every new trip waits for it: here a call takes —, while all our own code on a new trip takes —.

    Needed when: new trips arrive faster than that, or the plan needs a truck profile (height, weight, hazardous loads) or a latency promise.

    Here: the OSRM_URL environment variable; the code does not change.

  3. Stations in PostGIS

    Solves: numpy checks every station inside the route's box. That is fast for the — usable (geocoded) stations of the price file, but it grows with the number of stations.

    Needed when: the station list grows a lot (a national feed) or prices change many times a day.

    Here: stations in PostgreSQL with a spatial index; “stations near this line” becomes one indexed query and a price change is a row update.

  4. Several instances behind a load balancer

    Solves: one process answers a limited number of requests: at most about — plans from the cache per second, or — what-if replans per second (measured inside the process, without sockets: an upper bound), and holds — of memory (measured above).

    Needed when: steady traffic gets close to that.

    Here: the API keeps no state besides its caches (shared in Redis, first step) and the station data is read-only, so more instances give more throughput.

  5. A queue for batches

    Solves: planning many trips at once (tomorrow's dispatch) would hold connections open and send bursts to the routing server.

    Needed when: clients send trips in batches, or plans are wanted ahead of time.

    Here: accept the batch and return a job id; workers plan at the pace the routing server allows and say when it is done.

  6. Precompute frequent corridors

    Solves: the slow part of a new trip is the routing call, and fleets drive the same lanes every day.

    Needed when: a few lanes carry most of the traffic.

    Here: route those lanes ahead of time (and again when prices change); every request is then a cache hit or a what-if: — of our code, no external call.
